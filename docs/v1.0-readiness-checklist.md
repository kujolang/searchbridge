# SearchBridge v1.0 readiness checklist

This is the remaining work between the qualified 0.4.0 codebase and a credible
v1.0 release. It is written for a future agent to execute. A checked item must
have committed evidence; implementation alone is not enough.

The owner-approved, no-extra-cost provider scope and execution order are in
[v1.0-no-cost-execution-plan.md](v1.0-no-cost-execution-plan.md). That plan
controls provider selection and spending; this document remains the complete
readiness inventory.

SearchBridge remains a local CLI/SDK for agents and CI. A hosted control plane,
multi-tenant isolation, hosted RBAC, service high availability, billing, and
data-residency administration are outside the v1.0 boundary.

## Current baseline

The repository-local architecture is complete and qualified. Fixture,
conformance, security-property, SDK, MCP, cache/replay, external-adapter,
performance, release-candidate, and cross-platform tests pass. The current
evidence is in [release-qualification-0.4.0.md](release-qualification-0.4.0.md)
and the completed work is in
[pre-live-production-roadmap.md](pre-live-production-roadmap.md).

The remaining work falls into four groups:

1. prove every claimed provider operation with sanctioned live accounts;
2. make unattended authentication practical for agents and CI;
3. finish the 1.0 version, compatibility, packaging, and publication path;
4. record independent security and clean-install release evidence.

## Definition of done

SearchBridge may be called v1.0 only when every P0 item below is checked and
linked from a final `docs/release-qualification-1.0.0.md` record. The release
must install without a repository checkout or a separately installed Kujo
runtime on every declared platform. Every advertised provider/capability pair
must have current live evidence or be clearly marked fixture-only, external,
experimental, or disabled.

The final release must preserve these non-negotiable properties:

- SearchBridge fetches and normalizes evidence; it does not interpret SEO
  performance.
- Provider failures degrade by capability and do not hide partial success.
- Calls, retries, rows, bytes, pages, polls, elapsed time, and paid units remain
  bounded.
- Credentials, provider request headers, raw credential-bearing URLs, and row
  data never enter logs or release artifacts.
- Every submission still requires `--act --yes` on each invocation.
- Read and write operations remain separate.

## P0.1 — Freeze the supported v1.0 product contract

- [ ] Write a v1.0 support matrix that names each supported operating system,
  CPU architecture, Kujo runtime, Node version, Go version, Rust toolchain, SDK,
  provider, capability, authentication mode, and cost class.
- [ ] Decide which providers are stable built-ins at 1.0. A provider without
  complete live evidence must be disabled or labeled accurately in `providers`,
  `capabilities`, `agent-catalog`, the README, schemas, and SDK documentation.
- [ ] Decide whether the signed Plausible adapter is a supported integration or
  only a reference package. If supported, add it to live qualification and the
  support policy. If it remains an example, do not imply first-party support.
- [ ] Record the Semrush decision. Keep live Semrush disabled and its evidence
  fixture-only unless commercial entitlement, retention, cache, and
  redistribution terms are approved in writing. v1.0 may ship without live
  Semrush if all public surfaces say so.
- [ ] Freeze the v1 result, row, submission, discovery, batch, evidence-query,
  MCP, adapter, replay, task-state, and provenance contracts. State which
  additive changes are allowed in 1.x and which changes require 2.0.
- [ ] Publish a support and deprecation policy: supported 1.x window, security
  update policy, provider-removal process, adapter deprecation notice, and the
  status of pre-1.0 contracts.

Completion evidence:

- A committed support matrix and compatibility policy.
- Generated catalog, schemas, SDKs, README, and docs agree with it.
- A test fails when an advertised stable provider/capability lacks its required
  evidence classification.

## P0.2 — Make authentication work in unattended CI

The current scheduled workflow accepts bearer tokens and API keys from GitHub
secrets. Static Google OAuth access tokens expire too quickly for a dependable
weekly job. v1.0 needs a supported non-interactive credential path, not manual
token replacement before each run.

- [ ] Choose and document the supported non-interactive authentication method
  for Google Search Console and Google Analytics 4. Prefer a short-lived token
  minted by a CI pre-step, workload identity, or a least-privilege service
  account. Do not add interactive login or persist refresh tokens in
  SearchBridge.
- [ ] Define the equivalent CI credential lifecycle for Bing Webmaster and any
  other expiring bearer-token provider. Prefer an API key when the provider and
  required operations support it.
- [ ] Update `live-contracts` so it obtains or receives fresh credentials at
  run time and never prints them. Keep provider accounts, service-account files,
  refresh tokens, and credential-bearing URLs out of the repository and
  artifacts.
- [ ] Add an authentication preflight for every live provider. It must report a
  redacted, provider-scoped failure and must not block unrelated capabilities.
- [ ] Document local-agent and CI examples for every authentication mode,
  including credential rotation, revocation, least privilege, and failure
  recovery.

Completion evidence:

- A scheduled run succeeds without a person refreshing a token.
- A forced expired/invalid credential produces only redacted, capability-level
  degradation.
- Secret scanning confirms that no credential material entered git history or
  uploaded artifacts.

## P0.3 — Prove the complete live operation matrix

The existing workflow probes one operation for each of nine providers. That is
not enough to prove every advertised operation. Expand the live harness so each
row below produces a sanitized evidence record.

| Provider | Operation/capability still requiring live proof |
| --- | --- |
| Google Search Console | `search-analytics` / `search.performance`; `inspect-url` / `url.inspection` |
| Google Analytics 4 | `run-report` / `analytics` |
| PageSpeed Insights | `run-pagespeed` / `page.performance`, both declared strategies if both are supported |
| Chrome UX Report | `query-record` / `field.performance`, every declared form factor |
| Bing Webmaster | `query-stats` / `search.performance`; `link-details` / `backlinks` |
| Ahrefs | `all-backlinks` / `backlinks`; `keyword-overview` / `keyword.data` |
| DataForSEO | live organic / `serp.results`; standard async task / `rank.tracking`; search volume / `keyword.data` |
| SerpApi | Google organic / `serp.results` |
| Cloudflare | GraphQL HTTP requests / `edge.analytics`, including cursor behavior when available |
| IndexNow | controlled `submit-urls` / `index.submission` write probe |
| Bing Webmaster | controlled `submit-url` / `index.submission` write probe |
| Plausible | `stats-query` / `analytics` only if it is declared supported rather than a reference adapter |
| Semrush | Five disabled operations only after the external approval in P0.4 |

For each stable live operation:

- [ ] Use a dedicated least-privilege property, account, target, keyword, or URL
  that is safe for repeatable tests.
- [ ] Prove a successful bounded response and validate the public row schema,
  provider identity, source operation, provenance, pagination, telemetry, and
  cost metadata.
- [ ] Prove an empty but valid response without treating it as a transport or
  schema failure.
- [ ] Prove permission denial and invalid credentials degrade only that
  provider/capability and do not expose provider bodies or secrets.
- [ ] Exercise more than one page or cursor for every paginated operation. For
  naturally small properties, use a sanctioned provider sandbox or record why
  multi-page live evidence cannot be produced and retain the existing bounded
  transport proof.
- [ ] Verify observed calls and paid units never exceed the declared budgets.
  Compare estimates with provider receipts when the provider exposes them.
- [ ] Verify rate-limit handling from a provider sandbox, a sanctioned low-cost
  test, or retained real response-shape evidence. Do not intentionally create
  expensive traffic or risk account suspension.
- [ ] Upload only sanitized `searchbridge.live-contract-evidence/v1` records.
  Never upload rows, properties, URLs, keywords, provider bodies, or headers.

For write operations:

- [ ] Use disposable, operator-owned URLs and an approved provider account.
- [ ] Require `--act --yes`, exact capability authorization, call limits, and a
  one-host batch on the real path.
- [ ] Verify the receipt reports provider acceptance only and never claims that
  a URL was indexed.
- [ ] Confirm the same command without either confirmation flag performs no
  network call.

Completion evidence:

- A machine-readable operation matrix maps every stable catalog operation to a
  successful live evidence record and the required negative cases.
- The scheduled workflow fails when any stable operation is absent, stale, or
  schema-invalid; expected disabled/external operations are explicit skips.
- At least three consecutive scheduled runs pass after the final provider or
  contract change.

## P0.4 — Close provider policy and data-handling decisions

- [ ] Record the terms, plan entitlement, permitted automation, quota, cache
  retention, evidence retention, and redistribution decision for every stable
  provider. Link first-party sources and record the review date.
- [ ] Confirm whether normalized rows may be stored in local replay, CI
  artifacts, and operator backups for each provider. Set provider-specific
  maximum retention in the registry and test that replay cannot exceed it.
- [ ] Confirm whether fixtures are synthetic, licensed, or derived. Keep raw
  proprietary response samples out of the public repository unless publication
  is allowed.
- [ ] Complete the separate Semrush commercial and redistribution review before
  enabling any Semrush live operation or distributing Semrush-derived evidence.
- [ ] Add a release gate that rejects a stable live provider when its policy
  record is missing or past its review date.

Completion evidence:

- A provider-policy ledger is committed without confidential contract text.
- Registry retention settings, docs, fixtures, and release claims match the
  ledger.

## P0.5 — Perform the 1.0 version and compatibility migration

Changing `VERSION` alone will break adapter compatibility because the current
adapter gate requires the runtime and minimum supported version to share a
major version. Treat 1.0 as a migration, not a search-and-replace.

- [ ] Update all authoritative version surfaces: `VERSION`, `kujo.toml`,
  `src/core.kujo`, TypeScript package and lockfile, Rust package and lockfile,
  MCP server metadata, release metadata, badges, examples, and generated SDK
  artifacts.
- [ ] Replace hard-coded `0.4.0` extraction paths in platform workflows with the
  validated version read from `VERSION`.
- [ ] Update built-in and external adapter compatibility ranges for 1.x. Add
  migration fixtures covering supported pre-1.0 adapters, valid 1.x adapters,
  future majors, maximum versions, and deprecation/removal boundaries.
- [ ] Re-sign the Plausible reference manifest after any manifest change using
  the controlled private key. Ship only the public key/fingerprint and detached
  signature.
- [ ] Generate immutable 1.0 golden documents for every public envelope and row
  contract. Preserve the 0.2.x goldens as legacy-reader tests if 1.0 promises to
  read them; otherwise document the exact migration boundary.
- [ ] Replace the stale SDK manifest `contract_series` value with the declared
  v1 compatibility series and make generation/verification enforce it.
- [ ] Add one version-consistency gate that compares every package, runtime,
  MCP, bundle, and release version so future drift fails CI.
- [ ] Write `CHANGELOG` migration notes that distinguish stable v1 contracts
  from pre-1.0 behavior and name every intentional incompatibility.

Completion evidence:

- `searchbridge version`, all SDK package metadata, MCP initialize output,
  bundle manifests, SBOM, provenance, and release filenames report `1.0.0`.
- Adapter conformance covers both allowed and rejected cross-version cases.
- Fresh v1 SDK consumers compile against all v1 goldens.

## P0.6 — Finish public distribution

The current tag workflow matches only `v0.*.*` and publishes source archives.
A v1 tag would not run, and the release would omit the qualified runtime and SDK
packages.

- [ ] Change the release trigger to accept `v1.*.*` without weakening protected
  tag rules.
- [ ] Build release artifacts from the exact signed tag, not from an unbound
  branch checkout.
- [ ] Attach every declared runtime bundle, its checksum, TypeScript package,
  Rust crate, Go module/archive, aggregate checksums, SPDX SBOM, provenance, and
  signatures/attestations to the GitHub release.
- [ ] Decide the public SDK channels. Either publish to npm, crates.io, and the
  Go module proxy with provenance, or state that GitHub release assets are the
  supported channel. Do not imply registry availability before it exists.
- [ ] Complete package metadata needed by the chosen registries: repository,
  homepage, documentation, license files, included files, minimum runtime
  versions, keywords/categories where useful, and publish allowlists.
- [ ] Define the supported platform matrix. The current bundle builder supports
  Linux x64, macOS x64, macOS arm64, and Windows x64, while hosted smoke tests
  cover the architecture supplied by each runner. Add explicit jobs or remove
  unsupported claims. Add Linux arm64 only if it can be built, qualified, and
  maintained.
- [ ] Add clean-install tests that download each public artifact into an empty
  environment, verify its checksum and attestation, run `version` and `doctor`,
  execute a fixture offline, run the stdio MCP smoke, and execute one SDK
  consumer without a repository checkout or external Kujo installation.
- [ ] Document install, upgrade, rollback, and uninstall commands for each
  supported platform and SDK channel.

Completion evidence:

- A release workflow dry run or release candidate produces the complete v1
  artifact set from a tag-shaped ref.
- Independent jobs download and verify artifacts rather than testing only the
  build workspace.
- Installation instructions have been followed successfully on every declared
  platform.

## P0.7 — Complete independent security and release review

- [ ] Run a successful repository-wide security scan with the managed scanner
  or an equivalent independent review. The 0.4.0 assessment could not claim a
  managed deep-scan result. Triage, fix, and verify every release-blocking
  finding.
- [ ] Refresh the threat model after the final v1 provider, authentication,
  adapter, MCP, SDK, and release changes.
- [ ] Run CodeQL, dependency review, npm audit, cargo audit, `govulncheck`, secret
  scanning, property/fuzz tests, TLS/network fault tests, and the full validation
  suite at the final commit.
- [ ] Review all third-party runtime, SDK, action, and bundled licenses. Include
  required notices in released artifacts.
- [ ] Verify release workflows use pinned action commits and least-privilege
  permissions. Confirm no credential-bearing environment, cache, task state,
  provider row, or private signing key can enter artifacts.
- [ ] Build the release candidate twice from clean checkouts and require
  reproducible hashes for each deterministic artifact.
- [ ] Independently download and verify checksums, the signed tag, SBOM,
  provenance, attestations, archive contents, bundle manifests, and offline
  execution.
- [ ] Record rollback evidence using the last qualified 0.x bundle and a v1
  release candidate, including adapter and replay compatibility boundaries.

Completion evidence:

- `docs/security-assessment-1.0.0.md` contains no unresolved release-blocking
  finding or unclaimed required scan.
- `docs/release-qualification-1.0.0.md` links immutable CI runs and downloaded
  artifact hashes for the final commit.

## P0.8 — Make the released product usable without repository knowledge

- [ ] Rewrite Quick Start to begin with a released bundle or supported package
  channel instead of `git clone` and a separately installed Kujo runtime.
- [ ] Add provider-by-provider authentication and least-privilege setup guides,
  with copyable local-shell and CI examples that never include real secrets.
- [ ] Add complete agent setup for stdio MCP and direct CLI use, including tool
  discovery, timeouts, output budgets, partial failures, cancellation, and the
  separate write-confirmation boundary.
- [ ] Add one clean consumer example for each supported SDK. Each example must
  install from the public channel, invoke a released local binary, stream JSONL,
  handle typed failures, and run in CI.
- [ ] Add troubleshooting for authentication expiry, missing capabilities,
  provider outages, rate limits, paid-call preflight, replay corruption,
  adapter trust failure, and schema drift.
- [ ] Replace stale README links to old release checklists and session backlogs
  with the v1 support, operations, security, and release documents.
- [ ] Review every public claim against actual live evidence and distribution.
  Remove words such as supported, stable, verified, or available when the proof
  applies only to fixtures or local packaging.

Completion evidence:

- A new user can install, run a fixture, configure one live read provider, and
  connect one agent or SDK by following only released documentation.
- Documentation commands run in CI as executable examples.

## P0.9 — Cut and verify v1.0.0

- [ ] Merge all v1 work through the protected `main` branch with every required
  check green.
- [ ] Confirm the final commit has a clean working tree and no open critical or
  high dependency, code-scanning, secret-scanning, or validated security
  finding.
- [ ] Confirm the live operation matrix and provider-policy ledger are current
  and that the required consecutive scheduled runs passed.
- [ ] Create and push an annotated, verified signed `v1.0.0` tag from the exact
  qualified `main` commit.
- [ ] Let the release workflow publish the artifacts; do not hand-edit or
  replace files after attestation.
- [ ] Run independent release verification against the public tag and every
  downloadable artifact.
- [ ] Test a fresh install from the public release on every declared platform
  and through every declared SDK channel.
- [ ] Publish the final qualification, security assessment, migration notes,
  checksums, support matrix, and known limitations.
- [ ] Close or supersede old release-readiness documents so future agents have
  one authoritative backlog.

## Work order for a future agent

Execute the sections in this order:

1. P0.1 and P0.4: freeze claims and legal/policy boundaries.
2. P0.2 and P0.3: make credentials renewable and collect complete live proof.
3. P0.5: migrate contracts, adapters, goldens, SDKs, and versions to 1.0.
4. P0.6 and P0.8: finish distribution and clean-user documentation.
5. P0.7: perform final independent security and release qualification.
6. P0.9: tag, publish, download, and verify v1.0.0.

For every work packet:

- start from current `main` and use a short-lived branch;
- preserve fixture-first tests, bounded requests, redacted errors, and explicit
  write confirmation;
- never commit or log provider credentials, service-account files, refresh
  tokens, IndexNow keys, request headers, private signing keys, or raw
  credential-bearing URLs;
- run focused tests, then `bash scripts/validate.sh`;
- commit in small units, push, and leave the working tree clean;
- update this checklist only when the evidence exists.

## Not required for v1.0

These may be useful later but are not release blockers for the declared local
CLI/SDK product:

- a hosted multi-tenant service or web dashboard;
- hosted user accounts, billing, RBAC, HA, or data-residency controls;
- every possible SEO provider or metric;
- interpretation, ranking advice, recommendations, or SEO scoring;
- live Semrush support when it remains explicitly disabled and fixture-only;
- additional CPU architectures that are not listed in the v1 support matrix.
